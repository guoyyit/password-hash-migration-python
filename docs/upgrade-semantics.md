# 透明升级语义

## 基本流程

`verify(username, password)` 在单个可重入锁 + 单个原子事务中完成：

1. 账号不存在 / 已禁用 / 正锁定 → 直接返回相应结果并记录审计；
2. 用该账号 **当前存储的算法** 验证口令；
3. 口令错误 → 增加 `fail_count`，达到阈值则设 `locked_until`；
4. 口令正确 → 记录 `verify_success`，随后判断是否需要升级；
5. 若凭据为“陈旧”且升级策略允许，则在 **同一事务** 中重算为当前默认算法，
   独立复检新凭据，并 `rehash_epoch += 1`；
6. 提交事务并返回成功。陈旧但本轮未被策略抽中时，用户 **仍可正常登录**，
   下次登录再尝试。

“陈旧”的判定：算法名不等于当前默认算法，或成本参数（如 PBKDF2 迭代次数）
低于默认成本。

## 并发与交错

- 进程内所有验证/改密/重置/禁用都串行化在同一把 `RLock` 上；
- 并发登录时，只有一个事务能完成升级（`rehash_epoch` 恰好 +1），
  其余线程只会看到升级前或升级后的 **完整一致** 凭据；
- 登录与改密/重置交错时，最终状态永远是“当前口令 + 默认算法”，
  旧口令立即失效，不存在可被新旧口令同时接受的中间态。

## 成功不回退，失败记账

- 先验证后重算：只有验证已经成功才进入重算路径；
- 重算自身异常（如哈希服务瞬时不可用）会被捕获：保留旧的、已验证成功的凭据，
  记录 `rehash_failure` 后提交——**本次登录依然返回成功**（`migrated=False`）；
  下一次登录会再次尝试，直到升级成功；
- 失败计数只由“口令错误/锁定中尝试”驱动；重算路径不会重置或绕过计数
  （成功验证清零是验证语义，而不是重算的副作用）。

## 升级节奏（避免突发负载）

`ServiceConfig.migration_mode`：

| 模式 | 行为 |
| --- | --- |
| `ALWAYS`（默认） | 每次命中陈旧凭据的成功登录都重算。 |
| `SAMPLED` | 以 `migration_sample_rate`（0–1）概率重算；配合 `batch_size` 控制每个滚动窗口内最多升级多少账号，`reset_migration_window()` 开启下一窗口。 |
| `OFF` | 关闭登录时自动升级；旧账号永远可登录。仍可调用 `run_upgrade_batch()` 做受控批量升级。 |

`run_upgrade_batch(credentials, limit)` 使用运维提供的当前口令，
按 `limit` 小批量、按策略节流地升级账号；口令只瞬时使用，不落盘。
未升级账号的正常登录不受影响。

## 新增算法

- 通过 `service.register_algorithm(hasher, set_default=True)` 运行期登记新算法；
  旧算法的验证器仍然保留，旧数据继续可验证，新口令自动采用新默认算法。
- 即使凭据引用了当前进程尚未登记的算法，记录也不会被破坏：验证按失败处理，
  待算法注册后即可恢复验证并透明升级。
- 现有算法：
  - `pbkdf2_sha256`（当前默认，成本参数 `iterations`）
  - `scrypt`（参数 `n/r/p/dklen`）
  - `legacy_sha256_salted` / `legacy_sha256_unsalted`（仅用于验证历史数据，恒判陈旧）
